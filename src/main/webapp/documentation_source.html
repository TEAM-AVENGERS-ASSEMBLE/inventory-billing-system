1. Abstract Overview & Scope (0.5 Page)

The Inventory & Billing System is a full-stack, enterprise-grade retail automation system developed to bridge the critical operational divide between shop-floor inventory management and front-counter Point of Sale (POS) operations. Built strictly in accordance with a "Zero External Frameworks" engineering ethos, the entire platform relies upon foundational enterprise technologies: Java Servlets (Servlet 4.0 API), JDBC (java.sql.*), a transactional MySQL (InnoDB) database, and vanilla HTML5/CSS3/JavaScript.

Core Innovation: Unification of itemized customer checkout, real-time stock deduction, and immediate commercial tax invoice generation within a single atomic database transaction.

Traditional software in this sector suffers from bloated dependencies and high latency. This system eliminates overhead by dispatching single-request checkouts via lightweight JSON endpoints. Key features include an interactive billing screen with live quantity bounds-checking, an automated Low-Stock Warning Center flagging items where stock reaches safety thresholds, a formal Commercial Tax Invoice with dynamic Indian currency words conversion, and an executive Business Analytics suite generating End-of-Day (Z-Reports), Weekly, and Monthly turnover summaries.

2. Problem Statement Background & Challenges (0.5 Page)

Across small-to-medium retail enterprises, convenience stores, and neighborhood retail outlets, daily transactions and inventory tracking are heavily reliant upon manual paper logs, physical ledger registers, and standalone calculators. This archaic operational paradigm gives rise to severe operational vulnerabilities:

Key Pain Points Identified in Current Systems:
  1. Absence of Live Stock Visibility: Shopkeepers remain unaware of real-time inventory balances until manual physical counts are conducted. Consequently, items run out of stock during peak operational hours without prior warning, resulting in lost sales, unfulfilled orders, and customer dissatisfaction.
  2. Manual, Error-Prone Invoicing: Handwritten bills and mental arithmetic under rush-hour conditions lead to frequent calculation errors in line items, discount deductions, and GST computations. These inaccuracies directly harm store profitability and undermine customer trust.
  3. Zero Low-Stock Warning System: Fast-moving goods deplete completely with no warning or threshold notification. Without automated alerts, store managers cannot reorder inventory from suppliers in time.
  4. Opaque Business Performance: Determining daily sales revenue, tracking weekly volume trends, or identifying top-selling items requires hours of manual ledger auditing at the end of each working day.
Problem Summary: The absence of an integrated, real-time digital link between billing and inventory causes stock depletion, financial leakage, and operational blindness in small retail operations.

3. Objective System Goals & Scope (0.5 Page)

The principal objective of the Inventory & Billing System is to engineer a compact, zero-framework web platform that digitizes and unifies inventory control and point-of-sale billing into a synchronized, instantaneous workflow.

Specific Functional Objectives:
  • Single-Request Atomic Checkout: Execute cart checkout, customer receipt generation, and inventory deduction concurrently in a single atomic HTTP transaction to guarantee data synchronization.
  • Strict Zero-Framework Compliance: Implement the full stack using native Java Servlets, standard JDBC, and vanilla JavaScript without external web frameworks (Spring, Hibernate, etc.).
  • ACID Data Integrity: Enforce row-level database locking (SELECT ... FOR UPDATE) and transaction rollback to eliminate race conditions, double-selling, and negative inventory states.
  • Automated Threshold Warning Center: Provide visual alert badges and a dedicated management panel that automatically flags any product whose available quantity drops to or below its defined threshold.
  • Formal Commercial Tax Invoice: Render compliant tax invoices complete with registered GSTIN, CGST/SGST breakdowns, legal terms, and dynamic Indian currency words conversion.
  • Executive Managerial Analytics: Provide real-time reporting dashboards for End-of-Day (Z-Reports), 7-day weekly trajectories, and monthly category turnover.
Target Scope: Single-store and multi-counter retail establishments requiring high-throughput, low-latency POS billing without complex server infrastructure.
4. Working Principle Architectural Mechanics (0.5 Page)

The system operates on a Model-View-Controller (MVC) Client-Server Architecture utilizing HTTP/JSON as the transport contract. The client layer acts as an asynchronous presentation surface, while the server coordinates business rules and database persistence.

Core Working Principles & Execution Pipeline:
  1. Stateless Presentation Layer: The browser loads a unified SPA (Single Page Application) built with semantic HTML5, CSS3, and ES6 JavaScript. The POS interface maintains an in-memory cart with live client-side validations against catalog stock boundaries.
  2. Lightweight Request Dispatching: Upon cashier checkout, the frontend packages order metadata and line items into a compact JSON payload, dispatched via the standard Fetch API to /api/billing.
  3. Servlet Controller Orchestration: BillingServlet intercepts the POST request, deserializes JSON via Google Gson, validates input parameters, and hands control over to the Data Access Layer (SaleDAO).
  4. Isolated JDBC Transactional Pipeline: The backend disables auto-commit (conn.setAutoCommit(false)), obtains a shared database connection, applies pessimistic row locks to product records, deducts inventory, records master sales and line item records, and commits atomically.
Core Axiom (Slide 5 Flow): "The Servlet reads the order, JDBC updates MySQL, stock is deducted, and a receipt is generated and sent back — all in a single request."

6. Synchronization & Shared Database Concurrency & Data Integrity (0.5 Page)

The platform relies upon a normalized, shared relational MySQL database managed by the transactional InnoDB engine. Because inventory levels and sales invoices represent interdependent financial artifacts, strict synchronization mechanisms are implemented:

Concurrency Control & Synchronization Strategies:
  • Pessimistic Row-Level Locking: Before decrementing stock, SaleDAO issues a SELECT ... FOR UPDATE query on target product IDs. This establishes exclusive row locks in InnoDB, serializing concurrent checkouts and preventing phantom reads or negative inventory states.
  • Strict Referential Integrity: Foreign key constraints enforce strict parent-child linkages: sale_items.sale_id → sales.id (ON DELETE CASCADE) and sale_items.product_id → products.id (ON DELETE RESTRICT), preventing accidental deletion of products with historical transactions.
  • Automated Atomic Rollbacks: If any item in a multi-item cart experiences insufficient stock during execution, an IllegalStateException is thrown, executing conn.rollback() immediately. This guarantees that stock is never partially deducted.
Relational Schema Structure (Siddhesh Jagtap):

products (id PK, sku UK, name, category, price, stock_quantity, low_stock_threshold)
sales (id PK, invoice_number UK, customer_name, subtotal, tax, grand_total, sale_date)
sale_items (id PK, sale_id FK, product_id FK, product_name, unit_price, quantity, total_price)

7. Algorithm & Pseudocode Transaction Logic (0.5 Page)

The atomic billing algorithm coordinates stock validation, inventory decrement, invoice creation, and rollback handling.

ALGORITHM ProcessSaleAndDeductInventory(SaleRequest order): Input: order containing CustomerDetails and List<SaleItem> items Output: CompletedSale record with invoiceNumber OR Error with Rollback IF order.items IS NULL OR order.items.isEmpty() THEN THROW ValidationError("Cart is empty") TRY: conn = DBConnection.getConnection() conn.setAutoCommit(false) // Begin ACID Transaction // Phase 1: Verify and lock stock for each line item FOR EACH item IN order.items: row = EXECUTE "SELECT stock_quantity, price FROM products WHERE id = ? FOR UPDATE" (item.productId) IF row.stock_quantity < item.quantity THEN conn.rollback() THROW ShortageError("Insufficient stock for " + item.productName) // Deduct inventory stock in MySQL EXECUTE "UPDATE products SET stock_quantity = stock_quantity - ? WHERE id = ?" (item.quantity, item.productId) // Phase 2: Compute totals and generate unique invoice number order.invoiceNumber = GenerateInvoiceCode("INV-", CurrentTimestamp(), UUID()) order.tax = Round(order.subtotal * 0.05, 2) order.grandTotal = (order.subtotal + order.tax) - order.discount // Phase 3: Insert master sale record and line items saleId = EXECUTE_INSERT "INSERT INTO sales (...) VALUES (...)" FOR EACH item IN order.items: EXECUTE_BATCH "INSERT INTO sale_items (sale_id, product_id, ...) VALUES (...)" (saleId, ...) conn.commit() // Atomic Commit across all tables RETURN order CATCH Exception e: IF conn != NULL THEN conn.rollback() RETHROW e
Complexity Analysis: Time Complexity is $O(N)$ where $N$ is the number of cart items. Lock duration is sub-millisecond per row.
8. Java Implementation Servlet & Connection Core (0.5 Page)

The Java backend implementation starts with DBConnection.java and the primary REST endpoint BillingServlet.java.

package com.inventory.servlet; import com.google.gson.Gson; import com.inventory.dao.SaleDAO; import com.inventory.model.Sale; import javax.servlet.annotation.WebServlet; import javax.servlet.http.*; @WebServlet("/api/billing") public class BillingServlet extends HttpServlet { private final SaleDAO saleDAO = new SaleDAO(); private final Gson gson = new Gson(); protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException { resp.setContentType("application/json;charset=UTF-8"); resp.setHeader("Access-Control-Allow-Origin", "*"); try { Sale saleRequest = gson.fromJson(req.getReader(), Sale.class); if (saleRequest == null || saleRequest.getItems().isEmpty()) { resp.setStatus(400); resp.getWriter().print("{\"error\":\"Cart has no items\"}"); return; } // Atomic single-step receipt generation & stock deduction Sale completed = saleDAO.processSaleTransaction(saleRequest); resp.setStatus(201); resp.getWriter().print(gson.toJson(completed)); } catch (IllegalStateException shortageEx) { resp.setStatus(409); // Stock Shortage Conflict resp.getWriter().print("{\"error\":\"" + shortageEx.getMessage() + "\"}"); } catch (Exception ex) { resp.setStatus(500); resp.getWriter().print("{\"error\":\"Transaction failed\"}"); } } }
Zero-Framework Architecture: Relies solely on native javax.servlet-api without Spring MVC runtime dependencies.

9. Implementation — Continued Transactional Data Access (0.5 Page)

The transactional engine resides in SaleDAO.java, executing pessimistic row-level locking, inventory decrements, and batch inserts.

public Sale processSaleTransaction(Sale sale) throws SQLException { Connection conn = null; try { conn = DBConnection.getConnection(); conn.setAutoCommit(false); // Step 1: Disable Auto-Commit for ACID guarantee String lockSql = "SELECT name, price, stock_quantity FROM products WHERE id = ? FOR UPDATE"; String decSql = "UPDATE products SET stock_quantity = stock_quantity - ? WHERE id = ?"; try (PreparedStatement lockPs = conn.prepareStatement(lockSql); PreparedStatement decPs = conn.prepareStatement(decSql)) { for (SaleItem item : sale.getItems()) { lockPs.setInt(1, item.getProductId()); try (ResultSet rs = lockPs.executeQuery()) { if (!rs.next() || rs.getInt("stock_quantity") < item.getQuantity()) { throw new IllegalStateException("Insufficient stock for ID: " + item.getProductId()); } decPs.setInt(1, item.getQuantity()); decPs.setInt(2, item.getProductId()); decPs.executeUpdate(); // Step 2: Decrement stock immediately } } } // Step 3: Insert master invoice and batch line items String saleSql = "INSERT INTO sales (invoice_number, customer_name, subtotal, tax, grand_total) VALUES (?,?,?,?,?)"; try (PreparedStatement sPs = conn.prepareStatement(saleSql, Statement.RETURN_GENERATED_KEYS)) { sPs.setString(1, sale.getInvoiceNumber()); sPs.setString(2, sale.getCustomerName()); sPs.setDouble(3, sale.getSubtotal()); sPs.setDouble(4, sale.getTax()); sPs.setDouble(5, sale.getGrandTotal()); sPs.executeUpdate(); ResultSet keys = sPs.getGeneratedKeys(); if (keys.next()) sale.setId(keys.getInt(1)); } conn.commit(); // Step 4: Atomic Commit return sale; } catch (Exception e) { if (conn != null) conn.rollback(); // Step 5: Rollback on any failure throw e; } }
10. Implementation Explanation Code Mechanics & Rationale (0.5 Page)

The Java implementation leverages core JDBC and Servlet mechanisms to enforce consistency, concurrency control, and modular software boundaries:

Detailed Architectural Decisions & Mechanics:
  • Transactional Atomicity (conn.setAutoCommit(false)): In default JDBC mode, each SQL statement auto-commits individually. By setting auto-commit to false, stock updates and invoice creation are grouped into one atomic transaction unit. If any operation fails, the entire transaction rolls back cleanly.
  • Pessimistic Row-Level Locking (FOR UPDATE): Placing a lock query on the product row locks the specific tuple in InnoDB's buffer pool. Concurrent checkout requests targeting the same product wait sequentially, eliminating race conditions and negative inventory balances.
  • Auto-Generated Key Retrieval: Utilizing Statement.RETURN_GENERATED_KEYS during the sales master insert returns the database auto-increment ID, used immediately as the foreign key for inserting child records into sale_items.
  • Separation of Concerns: BillingServlet acts strictly as a web controller handling HTTP serialization, while SaleDAO encapsulates pure SQL data operations, adhering cleanly to the Single Responsibility Principle.
Error Segregation: Distinguishes business validation errors (stock shortages return HTTP 409 Conflict) from database errors (return HTTP 500), enabling user-friendly client feedback.
